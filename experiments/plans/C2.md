# C2. Codenames: LoRA fine-tuning of an embedding model on human games

## Question

Does fine-tuning Qwen3-Embedding-0.6B with LoRA on Cultural Codes training games predict human guesses better than the linear map on potion? The baseline is measured on C1's game split, not the 0.662 from the leaky split.

## Why it matters

Section 4 of `codenames/README.md` found that a linear map gains about 8 points on human guesses (on the leaky split). It also found that training on EAT wrecks Qwen3's human-guess score (0.495 to 0.167). A LoRA adapter can change the encoder itself, not just rotate its output.

- If LoRA beats the linear map, the bottleneck was capacity, and C4's "embeddings versus language models" comparison should use the tuned model as the embedding side.
- If it does not, a cheap map on a static table is as good a model of human guesses as a tuned 0.6B encoder at this data size. The README says so and stops tuning encoders.
- The secondary giver test asks whether a better guesser model makes a better giver, the open question from section 4.

## Design

- **Data.** C1's game split. Training rows come from train games only. The learning rate is chosen on val games. Test games are scored once.
- **Arms.** One factor changes between each pair:
  1. potion with the linear map (`train.py`, Cultural Codes only), the baseline;
  2. Qwen3-Embedding-0.6B untrained, query template;
  3. Qwen3 with the linear map, the same training rows as arm 1;
  4. Qwen3 with LoRA, the same training rows (the main arm);
  5. Qwen3 with LoRA, training rows plus EAT (`lora.rows` as it is now): an ablation of the data source.
- **Fixed settings** (from `lora.py`): rank 16 on q, k, v and o projections, α = 32, dropout 0.05, 7 hard negatives from the same board, MultipleNegativesRankingLoss, batch 64, warmup 5%, one epoch.
- **Learning rate.** One choice among 3e-5, 1e-4 and 3e-4, by validation log-likelihood with seed 1 only. The choice then holds for every seed and for arm 5.
- **Temperature and template** are fitted as in `study.calibrate`: τ on train, template on val.

## Primary metric and test

Top-1 match on C1's test turns, arm 4 minus arm 1, paired by turn. For each arm the per-turn hit is averaged over its seeds (three for LoRA, five for the map) before pairing. 95% interval by bootstrap over test games (10,000 resamples, seed 0). LoRA is said to beat the linear map if the interval lies above 0.

## Secondary metrics

- Arm 4 minus arm 3, the effect of LoRA over a map on the same encoder: the cleanest single-factor comparison.
- Arm 5 minus arm 4, the effect of adding EAT.
- Each arm's top-1 and log-likelihood on test, and top-1 on EAT held-out cues (`evaluate.association_top1`, the 984 cues of `norms.held_out`).
- Spread across the three LoRA seeds: each seed's top-1, and the range.
- **As a giver.** `train.codenames_scores` on 200 fresh boards (seed 2002), with clues limited to held-out EAT cues. Expected words found with the EAT guesser and with each of the seven other calibrated embedding guessers, arm 4 against arm 2, paired by board.

## Sample size

The test set is C1's: about 750 turns in about 79 games, with a half-width of 0.04 to 0.05 for a paired difference (C1's argument). That resolves a difference of 5 points or more. Three seeds measure how much LoRA training alone moves the score. Bouthillier et al. (2021) find that data sampling usually varies a result more than initialization, and the test-game bootstrap covers data sampling. Five seeds would cost 70% more for a variance term that is likely the smaller one.

## Seeds

LoRA training seeds 1, 2 and 3. Seed 0 is not used, so no confirmatory run repeats a configuration anyone may have tried while writing `lora.py`. The linear maps are cheap and use seeds 1 to 5, as in C1. Board seed 2002, and bootstrap seed 0.

## Compute and cost

Hugging Face Jobs, `a10g-small` ($1.00 an hour), through `hfrun.py`. The training set is about 6,000 rows (C1's train games), and one epoch of a 0.6B model with LoRA at batch 64 should take minutes. Encoding about 17,000 words twice takes a few more. Estimate: three learning rates plus four confirmatory runs (arm 4 at three seeds, arm 5 at one), each under 20 minutes, about 2.5 GPU hours or $2.50. Hard cap $4, enforced by a 30-minute timeout per job and no more than 8 jobs. The arms without LoRA run on CPU here. This plan needs approval before its jobs, since it alone is above the $3 shared limit with C4.

## Entry points

`lora.py` exists. To be added:

- `--sources cultural|cultural+eat` and `--scheme game` on `lora.rows`, and `--lr`.
- `--evaluate OUT`: after training, score the tuned vectors on val (for the learning-rate choice) or test, inside the job, since the machine that writes the README cannot reach huggingface.co. It writes `scores.json` with per-turn hits, so pairing and bootstrap happen afterwards on CPU.
- Launch, for each seed: `hf jobs uv run --flavor a10g-small --timeout 30m -e COMMIT=<sha> -e GROUP=codenames-gpu -e EXPERIMENT=c2 -e RUN=lora-s1 --secrets HF_TOKEN experiments/hfrun.py codenames.lora --scheme game --sources cultural --lr <chosen> --seed 1 --evaluate test --out-dir OUT`. The job also needs `sentence-transformers[train]`, `peft` and `torch`. They go in a `codenames-gpu` dependency group, so that `hfrun.py` can install them with `GROUP`.
- `python -m codenames.c2 --runs <downloaded scores> --out codenames/results/c2.json`: pairing, bootstrap and the tables.

## Outputs

- In git: `codenames/results/c2.json`, with per-arm top-1, intervals and the per-seed numbers, and a README section.
- In the private dataset, under `runs/c2/<run>/`: the tuned vectors (`.npz`, about 70 MB each), the adapter weights, per-turn scores, the training log and `manifest.json`. Qwen3-Embedding is Apache 2.0, but the adapters were trained on Cultural Codes, whose license is unstated, so they are not published.

## Stopping rules and a null result

If the chosen learning rate gives a validation log-likelihood below the untrained model's, training is judged to have failed. C2 then reports that, without testing, and does not try other settings on test. If the primary interval includes 0, the README reports that LoRA did not beat the linear map at this data size and gives the interval and the per-seed scores. A job that hits its timeout is rerun once; a second failure is reported as a failure.

## Threats to validity

- **Hyperparameters.** Only the learning rate is tuned, over three values. Another rank or more epochs might do better. The claim is limited to this configuration.
- **Unequal baselines.** The linear map uses all 24 other board words as negatives and LoRA uses seven. That is part of each method as written, and the plan does not equalize it.
- **One encoder.** harrier-oss-v1-0.6b is the natural second encoder. It is left out to stay inside the budget and would be a separate plan.
- **Precision.** Training is bf16 or fp16 and vectors are stored as float16, as `lora.py` does now. The untrained arm uses vectors made the same way.

## Amendment, 2026-11-19

Recorded after C1 was merged and before any run on its split. None of these changes the primary metric or its test.

- **Data size.** C1's game split has 4,820 train turns, 717 val turns and 551 test turns in 68 test games, not the 6,000 rows and 750 turns in 79 games this plan expected. Arm 5 adds 23,513 EAT rows, 28,333 in all.
- **Arms 1 and 3 are C1's.** C1 trained the potion map and the Qwen3 map on the same train turns with seeds 1 to 5 and scored them on these test turns once (`results/train-potion-game.json`, `results/train-Qwen--Qwen3-Embedding-0.6B-game.json`). C2 pairs with those per-turn hits instead of scoring the test turns a second time. Arm 3's vectors come from the CPU runner, as in C1, not from the GPU job.
- **Arm 2 is encoded inside each job**, before the adapter is added, with the same code and precision as the tuned vectors. Its test score comes from the seed-1 test job; the other test jobs report it too, as a check on how much GPU nondeterminism moves it.
- **Templates.** Each job encodes the clue side with the bare, related and query templates and the words bare, as `study.calibrate` does for Qwen3. τ is fitted on train and the template chosen on val, for the untrained and the tuned vectors alike.
- **Where scoring happens.** The jobs write per-turn hits and log-probabilities (`codenames.c2`). The learning-rate jobs use `--evaluate val` and never read the test turns. For the giver test, the job records the clue and count each model gives on the 200 boards of seed 2002; the expected scores with the other guessers are computed afterwards on CPU from `results/calibrate-game.json`.
- **Precision.** Training uses bf16 autocast on the A10G; vectors are encoded in float32 and stored as float16.
- **Pilot (exploratory).** One job on the published split, learning rate 1e-4, seed 0, scored on the published val turns, to time the job. Seed 0 is not used by any confirmatory run. Its numbers are not reported as a result.
- **Budget.** The owner approved a hard cap of $4 for C2 in total, the pilot included.
